# 06_Small-Goal Progress

> Purpose: help the student immediately recognize what they just learned or accomplished, then show it with a module mastery bar and current skill checklist. These are separate levels, never convertible counts.
> Chinese version: [`06_小目标进度.md`](./06_小目标进度.md)

## 1. Two layers: module bar and small-goal checklist

A **module** is a bounded knowledge range inside one subject (e.g. "list methods", "linear equations in one variable", "everyday conversation"). It contains several **knowledge units** and smaller **small goals**. A module is **not** the current task, the current round, or the whole subject.

The **module bar** tracks module mastery: `K` = knowledge units formally mastered inside the module, `T` = units defined by the course route. Fill `floor(10*K/T)` of ten cells and label it `K/T knowledge units mastered`.

The **small-goal checklist** (section 2) holds the concrete skills the student is working on right now. Checklist ticks are **never** converted into module progress, and the bar never moves because of one tick.

Unit records and weighting:

- Module name, boundary, unit list, and the "units are equally weighted" rule live in the **existing course route** `00-课程路线.md`. Do **not** add a state store, authoritative mastery table, or progress database.
- By default a unit is a **named** lesson/knowledge unit in the route. Unmastered units still belong to `T`; only formally mastered units enter `K`. Derive `K` from the 📊 mastery table and answer documents' final re-assessments, **not** an accuracy rate or probabilistic mastery score.
- If the module is undefined (no module or unit list in the route) or evidence is missing, write **"module progress undetermined" / "module progress needs checking"** instead of a denominator or a percentage. If planning is missing, teach the current content first; do **not** force a long upfront plan before an introduction.

## 2. The current small goal: 2-4 concrete skills

Write 2-4 skills, **usually 3, or 1 for a tiny goal**, without padding or splitting one ability into several lines. Each is observable: explaining a specific definition, performing an operation, deriving a step, or expressing a particular meaning. Avoid vague claims such as understanding or finishing the topic.

Skill lists exclude **process items**: no "finish the task", "hand in homework", "pass verification", or "complete the exercises". **Formal verification is a background condition; it never enters the skill list and is never the last skill.**

Ticking and completion:

- Each skill needs the student's **original answer** plus a **formal assessment on the applicable dimensions** for that subject. An **introduction answer is labelled "initial observation" only and does not count as mastery**; a **prompted success does not tick** an independent skill.
- The small goal closes only when **every issued formal round passes**; all ticks then give a clear sense of completion. When a skill still awaits independent or integrated verification, say so in **one short note** instead of faking full mastery.

The module bar advances separately and under stricter terms:

- `K` increases by one only when **all conditions for that unit are met and its whole lesson passes final re-assessment**.
- Assign required Feynman/integration closing work upfront to a unit's exit conditions or a verification unit. That unit cannot enter `K` before passing, so the bar stays incomplete. If an older route omitted required closing work, show scope needs checking and explain the omission; do not draw a bar inconsistent with `K/T` or silently enlarge the denominator.
- So when all skills of the current small goal are ticked, the module bar may **not move at all**; a full bar appears only when the module truly completes.

## 3. Two layers at the top, shared by chat and both documents

Keep three fixed pieces of information in this order:

1. **Module heading + module bar**: the module name, then one line with the ten-cell bar and `K/T knowledge units mastered` ("module progress undetermined" when the module is undefined).
2. **Small-goal heading + skill checkboxes**: the current small goal, followed by 2-4 `- [x]` / `- [ ]` lines.
3. **One next-step line with a short evidence note**: `> Next: ... Evidence: ...`.

- The module bar sits **above the small-goal heading**, **not below it**; the small-goal area carries **no local `k/N` and no second bar**.
- Briefly identify both module mastery evidence and current skill assessment, such as meet-lists final re-assessment and current round 1. Label entry observations or unverified skills honestly; do not create another report.
- Use a **bold heading line in chat** and an **H2 in documents**; all three surfaces must match in content, while level and font may differ.
- Use a monospaced `██████░░░░`; where blocks are unsupported, use `#`/`-` for the same ten cells, and fall back to completed/pending labels where checkboxes are unsupported. The tutor updates from evidence; the student need not tick boxes manually.
- Let Markdown wrap naturally for narrow screens; avoid wide tables, drawn frames, and space-based alignment.

| Surface | Position | Contents |
|---|---|---|
| Chat | Block start, skill or unit-count change, stopping, resumption | Both layers plus next step; repeat the full view only when needed |
| `01_教学引导.md` | After the title, before the body | The same two layers, then explanations |
| `01_学生回答.md` | After the title, before questions and original answers | The same two layers, then this round's work and appended assessments |

Both documents place the whole block between these two comment lines, with one current view per document:

```
<!-- s2g-goal-view:start -->
(module heading + module bar + small-goal heading + skill checkboxes + next step)
<!-- s2g-goal-view:end -->
```

**Replace only that section** (a display snapshot); original answers, hint history, prior assessments, and appended historical snapshots stay untouched. If an older document lacks these comment lines, create one view after the title and preserve history. Use the same layout as the teaching and answer templates.

Keep the whole view **compact and necessary**: no achievement walls, dashboards, or duplicate task sections, and no compulsory eight sections or fixed item count; but never drop key principles, conditions, sources, prompts, or formal re-assessment for brevity.

## 4. Timely feedback and a sense of completion

**Recognize each substantive achievement before corrections or the next step.** Say what the student independently did, what result it produced, and which capability this demonstrates; briefly quote the actual answer when useful. Do not merely say correct or good job, wait for a bar change, or bury achievements under long grading. Preserve full formal assessments in the document; chat leads with the result and necessary corrections, still explaining important principles.

Tick a skill promptly when its evidence passes. A successful intermediate step deserves specific recognition, not a tick for the whole skill. Disclose help. An entry judgment can be recognized as correct while remaining an initial observation rather than formal mastery.

When all skills and issued formal rounds pass, explicitly close the small goal with the acquired capability. Calculate the module bar separately. Do not diminish the achievement or add surprise required work.

- **Block start**: show both layers first, then the short situation and one current question; never preview future prompts or empty rounds.
- **Across small goals**: the module count **persists** (it does not reset), while the small-goal heading and checklist are **replaced with new ones**; evidence for skills already learned stays in the answer document, **neither erased nor copied into the new checklist**.
- **Small goal complete**: when all skills and issued formal rounds pass, show the achievement and close the goal, keeping the module bar honest. If an issued verification still has not passed, state confirmed skills and pending verification without claiming closure.
- **Stopping point**: when every skill is ticked and all issued formal rounds pass, say plainly that the block is done and the student may stop; do not attach the next block's questions unless continuous study was agreed. If the module bar is also full, state separately what the module completion means.
- **Closing work unfinished**: a unit with previously agreed Feynman/integration verification pending remains unmastered. If an older route omitted it, explain that scope needs checking; do not add surprise work that diminishes the completed small goal.
- **When stuck**: shrink the exercise or change the explanation; do not expand the goal or add skills to manufacture progress.
- **If scope must change**: explain why, then start a separately named block or revise the unit list in the existing route and recalculate; never add surprise requirements near a full bar. Preserve prior results and unverified parts honestly.
- **Insufficient or conflicting evidence**: label the module "progress needs checking" instead of relaxing standards or inventing lesson or course denominators.

## 5. Evidence for ticks

| Situation | Update |
|---|---|
| An action was completed but the skill condition was not met | Recognize the step; keep the skill pending and the module bar unchanged |
| An introduction answer appears to support a skill | Add an "initial observation" label beside it and **leave the skill unticked**; tick it only after formal assessment in formal study, and never claim mastery from it |
| A prompted answer is correct | Mark the help; do not tick an independent skill |
| Claims of understanding, repetition of a tutor answer, or unreadable sources | Not evidence |
| Formal assessment passes | Map re-read answers and this round's assessment to skills; one answer may support several skills, and one skill may need several answers |
| A key conceptual or logical error remains after revision | Keep that skill pending; never relax the standard |
| New evidence overturns an earlier observation | Explain and revoke its tick while preserving prior records |
| All unit conditions are met and the whole lesson passes final re-assessment | Increase `K` by one and redraw the bar as `floor(10*K/T)`; derive this from route + 📊 + final re-assessment, never from checklist ticks |
| Module closing work (Feynman/integration) unfinished | Its unit has not met exit conditions and cannot enter `K`; an omission in an older route means scope needs checking, not fake full progress |

**Full-bar conditions**: the small goal shows all ticks only when every skill has evidence, the student completed the independent ones, and all issued formal rounds pass on applicable dimensions; a **full module bar additionally requires every module unit to be mastered and the closing verification to pass**. Completing a small goal is not whole-lesson mastery; 📊 "mastered" still requires final re-assessment.

## 6. Update flow, resumption, and reconciliation

Update order:

1. Read `01_学生回答.md` and preserve original answers and hints;
2. Re-read and assess on the applicable dimensions, then append this round's assessment and skill decisions;
3. Skill ticks come from **assessment results**; module `K/T` is derived independently from **course route + 📊 + the relevant whole-lesson final re-assessment**;
4. Derive one two-layer view from the latest evidence, update the answer document's top section, then read and update the teaching guide's top section;
5. **Re-read both to confirm they match**, then show the same view in chat.

- End each view with a short reference to both module mastery evidence and current skill assessment; label unknown scope, unverified skills, and initial observations honestly.
- If one write fails, identify the unsynchronized document and **never claim consistency**; read the actual files and repair from evidence without reverting answers or inventing assessments.
- **Do not resume from memory**: read `我的学习/我的规则.md`, the 🚦 handoff, and the evidence documents, then compare both document views; regenerate from evidence when they disagree.
- With an unknown module or conflicting evidence, show "module progress undetermined / needs checking" honestly on all surfaces. Add **no authoritative table**; 🚦 only references its owning document plus the current small goal and next step, while 📊 and ⏳ keep their roles per `03_落档事件表.md`.
- This section defines display and decision rules only; it **does not alter the existing structure or history of real student records**, and teaching or preference edits never touch unrelated files.

## 7. One tangible example

This fictional layout and feedback example is not a student record and must not be filed as real evidence.

**Situation**: a shopping list already contains bread and eggs, but milk was forgotten. Add one item at the end without rewriting or overwriting the original list.

**Assumed route and evidence**: Python lists has four equal units: meet lists, add, remove, and find. Only meet lists has passed final re-assessment. The add unit includes single-item appending and adding a batch; this small goal covers only single-item appending and does not pre-issue later questions.

The student independently writes `items.append("milk")`, verifies that bread and eggs remain and milk is at the end, and passes the current skills and formal rounds. Give feedback first:

> Bread and eggs are still there, and milk is now at the end. This small goal is complete: you can add an item to an existing shopping list without rewriting it.

Then synchronize the two-level view:

**Module: Python lists**

`██░░░░░░░░` **1/4 knowledge units mastered**

**Current small goal: append one shopping-list item**

- [x] Explain that `append` adds one element at the end
- [x] Distinguish appending from overwriting, retaining existing elements
- [x] Independently append an item and check the resulting list

> Next: this small goal is complete; you may stop here. Evidence: meet-lists final re-assessment and current skill assessments.

**All skills are ticked, yet the module bar stays at 1/4.** Batch addition remains unlearned, but single-item appending was fully accomplished; do not deny that achievement. After the whole add unit meets its conditions and passes final re-assessment, the bar becomes `█████░░░░░` **2/4**. The next small goal receives a new checklist while preserving the module bar and prior skill evidence.


## 8. Verification

Check that the module bar is derived from route + 📊 + final re-assessment (not converted from ticks), an undefined module honestly reads "undetermined / needs checking", skills are 2-4 concrete abilities with no process items, formal verification stays in the background instead of the checklist, every tick has original answers plus applicable-dimension assessment, hints are labelled honestly, `floor(10*K/T)` matches the drawn cells, no full bar or 100% appears while module closing work is unfinished, all three surfaces show matching two-layer views with only the display section replaced (student history intact), a stopping point exists, and resumption keeps the same scope. The checklist is not an extra exercise list: **rounds still issue only 1-3 questions and never pre-issue later rounds**. Improved goal and completion experience is a design hypothesis, not demonstrated learning-outcome evidence.
