# 03 · Design Notes (for authors and contributors)

> This document answers: **why it is designed this way**. Users don't need to read it.
> Chinese version: [`03-设计说明.md`](./03-设计说明.md)

---

## 1. What problem this project solves

Every AI learning tool on the market is solving "**give you content**".
But what actually stops people from learning isn't a lack of content — it's that **nobody is watching you, nobody is assessing you, nobody tells you where you went wrong**.

This project's assumption:

> **AI is already good enough at teaching; what's missing is a "teaching protocol that can run long-term".**

So this project **is not software**; it is **a set of Markdown protocols**:
drop it into a folder, and any AI that can read files becomes a one-on-one tutor.

---

## 2. Three core design decisions

### Decision 1: Markdown as the single source of truth, no App

| Option | Problem |
|---|---|
| Build a website/App | You must maintain servers, accounts, and user data is locked in your hands |
| Make it a prompt collection | The user has to paste manually every time, and state isn't persisted |
| **A Markdown folder (this option)** | ✅ The user owns the data; any tool can read it; switching tools loses no records |

**Cost**: no flashy interactions.
**Benefit**: zero operations, zero lock-in, still openable ten years from now.

### Decision 2: `AGENTS.md` as the single contract + auto-generated pointers

The problem: 25+ AI tools, each recognising a different rules file name.

| Option | Result |
|---|---|
| Copy a full set of rules into every tool | ❌ One change means 25 changes, and drift is inevitable |
| Write only `AGENTS.md` and ignore tools that don't read it | ❌ A large number of users can't use it |
| **Single contract + a script that generates pointers (this option)** | ✅ Change the rules in one place; switching tools costs nothing |

A pointer file contains just one sentence: "go read AGENTS.md", and it is generated by `_tools/setup-agents.mjs`.
**Adding a tool = change one array + re-run the script.**

### Decision 3: Three-dimension assessment + all-✅ to advance

The core mechanism inherited from the old project (the Java self-study system, validated over 22 lessons):

```
Conceptual understanding ／ Logical correctness ／ Formal correctness
        ↓ all three ✅
      only then may you advance to the next lesson
```

**Why the three dimensions must be independent**:

- Only "concept" → the student can talk but can't do
- Only "logic" → the student got it right but can't say why
- Only "form" → the student writes beautifully but understands it wrongly

**Why dimension ③ changes with the subject**: programming judges "does it compile", English judges "grammar", maths judges "derivation".
Hence `学科包/` — this turns that from a Java-only rule into something universal.

## 3. What was inherited from the old project, and what changed

### Inherited (validated over 22 lessons of real use)

| Mechanism | Origin |
|---|---|
| All three dimensions ✅ before advancing | The old project's main loop |
| The answer document = the only learning evidence | The old project's iron rule |
| Small problems fixed directly + three-part explanation | The old project's "direct-fix protocol" (the user's own words) |
| The filing event table (event → which file to write) | The old project's section 7 |
| State maintained in only three places (🚦/📊/⏳) | A lesson from the old project's anti-patterns |
| "After a change you must re-read the file" | The old project's hard rule 1 |
| Further reading precise to the chapter | The old project's route document's final section |

### Improvements (new in this project)

| Improvement | Why |
|---|---|
| **Subject packs** | The old project hard-coded Java criteria, so it couldn't generalise |
| **Multi-agent adaptation layer** | The old project only ran in DSH, so nobody else could use it |
| **Placement script** | The old project had only a one-off diagnosis, with no fixed script |
| **Framework/data separation** | The old project cloned one data set per clone, so framework updates conflicted |
| **Quality-check script** | The old project's 22 lessons had no automated checks, all manual |
| **Example demo** | Newcomers to the old project couldn't understand the structure |
| **Chinese and English editions** | Needed for open source |
| **Git version management** | The old project had **zero version management** (all evidence for 22 lessons relied on manual backups) — the biggest risk |

## 4. The reasoning behind the directory structure

```
StepsToGreat/
├── AGENTS.md              ← the single contract (AI entry point)
├── 协议/                   ← teaching rules (AI read-only)
├── 学科包/                 ← assessment criteria (AI read-only)
├── 模板/                   ← skeletons (AI read-only)
├── 示例/                   ← demo (AI read-only)
├── 教程/                   ← for humans (AI read-only)
├── _tools/                 ← scripts (AI read-only)
├── docs/                   ← compatibility matrix + ADRs
├── 我的学习/               ← all of the student's data (AI may write)
└── 资料/                   ← the student's material (append-only)
```

**The key division**: **read-only framework** vs **writable data**.

- Framework: updatable with `git pull`, never polluted by student data
- Data: goes into `.gitignore`, so a student never loses records from a framework update

---

## 5. Why these were deliberately excluded

| Excluded item | Reason |
|---|---|
| Built-in course content | Students bring their own material; stuffing in someone else's course is a distraction |
| Cloud sync | Data sovereignty belongs to the user; sync with their own cloud drive/Git |
| An auto-grading backend | The AI carries the grading logic; no server side is needed |
| A user account system | No server means no accounts |
| Interactive HTML courses | Markdown is the single source of truth; HTML is generated on demand, not persisted |
| A fixed question bank | There are too many subjects for a fixed bank to cover; the AI writes questions on the spot |

## 6. How to contribute

### Add a subject pack (the most valuable)

1. Copy `学科包/_自定义学科包模板.md`
2. Fill in the 6 sections (three-dimension definitions, criteria, high-frequency errors, question forms, verification methods, how to write further reading)
3. Save it as `学科包/<subject-name>.md`
4. Open a PR

**The test**: in this subject, what is a "structural error" (must lose points), and what is a "slip" (no points lost)?
If you can answer that, it's a good subject pack.

### Add an AI tool

Edit the `TARGETS` array and the `MATRIX` table in `_tools/setup-agents.mjs`, run the script once, and open a PR.

### Change the protocol

Before changing anything in `协议/`, please open an issue explaining **what scenario you hit what problem in**.
The protocol is a core asset, and changes propagate to every user.

### Run the quality check

```bash
node _tools/check.mjs        # full check
node _tools/check.mjs --quiet
```

Checks: fence parity, broken links, leftover placeholder words, UTF-8 without BOM, CRLF, pointer consistency, profile path existence.

## 7. Known limitations

| Limitation | Explanation |
|---|---|
| Depends on the AI's tool-calling ability | An AI that can't read or write files (pure chat) can only paste manually |
| Limited free quota | Reading 5–10 md files in one session eats credits → have the AI `read` on demand |
| Privacy | Most tools temporarily upload files for indexing; sensitive material needs a local model |
| Grading accuracy depends on the model | Weak models may misjudge → use a mid-tier model or better |
| No automated tests | Only `check.mjs` does format checks; teaching quality relies on the protocol's constraints |
| Performance on long Chinese documents | No vendor publishes quantitative data; free tiers are often bound to Auto / weak models, and long-instruction adherence is weaker (inference) |
