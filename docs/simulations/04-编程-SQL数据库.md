>
> **再对甲乙——这次你两个都预测错了：**
>
> | | 甲（条件在 `ON`） | 乙（条件在 `WHERE`） |
> |---|---|---|
> | 行数 | **4 行** | **1 行** |
> | 内容 | 张三/102/200、李四/NULL/NULL、王五/NULL/NULL、赵六/NULL/NULL | 张三/102/200 |

> ```
> 阶段一 · 配对（ON 管这里）
>   左表每行都拿出来，去右表找「符合 ON 条件」的行；
>   找不到也不影响 —— ON 的规矩是「配不上也照样出行，右边补 NULL」。

## 4. 本学科发现的优化点

### 4.1 学科包缺陷（`学科包/编程.md` 没覆盖到的情况）

#### 静默错误该算②还是③？——**算 ②，但必须明写，否则导师一定漂移**

依据链（文件原文，不是偏好）：

1. `编程.md` 第 1 节 ② 的定义原文是「算法/流程/边界/数据结构选择对，**能得到正确结果**」——**"能得到正确结果"本来就在 ② 里**。
2. `理科.md` 第 1 节已写透：「**② 判「结论对不对」，③ 判「写出来的过程规不规范」**……**这是本学科最常见的评分分歧点，必须分开标注**」。这套分工**可原样移植到 SQL**：② 判**结果集**对不对，③ 判 **SQL 能否被引擎接受、写法可不可移植**。

**但这句话只写在 `理科.md`，`编程.md` 里没有。** 本仿真实测到两处危害：

1. **判定漂移**——题 1 的 `JOIN` 丢王五：判 ② = "逻辑不通"（走 Socratic，正确）；判 ③ = 「语法可编译 → 能跑起来 → ✅」（也"正确"）。**导师被逼进"同一段话里既承认能跑、又判不通过"的自相矛盾**，而这正是学生质疑的来源。
2. **三维退化成二维**——SQL 里真正让人翻车的错（静默丢行/多行、`ON`/`WHERE` 错位、`NULL` 比较）**全部**落在 ②，③ 变成恒真维度。本仿真 3 题里 ③ 只在题 1 判过一次（还是因笔误代改）。而 `学科包/README.md` 第 5 节明令「不许……跳过维度③」——现状等于**跳过**。

#### ③ 叫「语法可编译」对 SQL 合适吗？——**不合适，这个名字不成立**

SQL **没有"编译"阶段**，`编程.md` 第 1 节 ③ 的定义「能在 IDE / 解释器里跑起来」只能勉强套用，且掩盖了 SQL 特有的第三类错误。本仿真四类都踩到了：

| 错误类型 | 例 | 报错？ | 现有判据 | 该判 |
|---|---|---|---|---|
| **① 显式语法错** | 全角逗号；`WHERE SUM(amount)>150` | ✅（SQLite `misuse of aggregate`；MySQL `Unknown column`） | ③ 能判 | ③ |
| **② 静默结果错** | `JOIN` 丢王五；`o.amount IS NULL` 多出李四 | ❌ 不报错，但结果错 | **判不了**（不在第 2 节任一清单） | **②**（须明写） |
| **③ 引擎方言依赖** | `SELECT o.amount … GROUP BY c.name`（bare column） | **看引擎**：SQLite 静默容忍；**MySQL 8.0 `ONLY_FULL_GROUP_BY` 默认开 → 报错** | **判不了** | **③**（"可移植性"是新判据） |
| **④ 语义模型缺失** | `NULL` 当 0；`NULL <> NULL` 结果是 NULL 不是 FALSE | ❌ 不报错，但结果错 | **完全没提** | ① 或 ② |

→ 第 ③ 类尤其关键：**一段 SQL 合不合法，取决于你连的是哪个数据库。** 协议与学科包**都没规定"以哪个 DBMS 为准"**，导师无从下判（本仿真导师只能自己拍"以 MySQL 8.0 为准"）。
**建议 ③ 对 SQL 改名「语法与可移植性」**：判 ① 目标 DBMS 能否**解析并执行**（不是"编译"）；② 写法是否**依赖未定义行为 / 引擎方言**（`GROUP BY` 漏列、隐式类型转换、`LIMIT` 方言、大小写敏感性）。

#### 结果正确性依赖数据 —— "有明确输入输出"这条对 SQL 不够

`编程.md` 第 4 节第 1 条是「有明确的输入输出（可验证）」，而 SQL 的**输入是数据集**（不是参数）、**输出是结果集**（不是标量）。同一句 SQL 在本数据集上给 4 行；把王五删掉仍可能给 3 行但**内容完全不同**——**不给数据，"结果对不对"根本不存在**。若不预先在真实引擎上跑，导师只能凭印象说"你错了"，**直接违反仿真纪律第 2 条**（本仿真跑了 16 组查询才敢下笔）。
→ 第 4 节需补：**题面必须附「数据集 DDL + 初始数据 + 期望结果集」三件套**。

#### SQL 是否需要「数据集 + 期望结果」格式？——**需要，且暴露出第四个信息源**

三维评分都在看"学生写的东西"，而 SQL 的判定需要**执行结果**。本仿真题 1 是铁证：学生的 SQL 与学生的期望**互相自洽**（期望 3 行、SQL 也跑出 3 行），**自检 100% 通过而答案全错**。只收 SQL 不收期望结果集，导师**根本区分不了**"写错了"和"想错了"。
→ 出题格式固定为**四元组**：`数据集` + `题目` + `学生的 SQL` + **`学生预测的结果集（几行 + 每行值）`**。**缺第四项不得判 ②。**

#### ⑤ 其他没覆盖的（第 3 节高频错误清单里**一条都没有**）

1. **`NULL` 三值逻辑**：`= NULL` / `<> NULL` 恒不成立；`NULL <> NULL` 结果是 NULL；`NOT IN (含 NULL 子查询)` 返回空集。
2. **`COUNT(*)` vs `COUNT(列)` vs `COUNT(DISTINCT 列)`**：实测 `LEFT JOIN` 后 `COUNT(*)` 给王五记 **1**（配 0 行也产 1 行），`COUNT(o.id)` 记 **0**——**两者都可能不是你想要的**。
3. **隐式逗号连接**漏条件 → 笛卡尔积（4×4 = **16 行**，实测）。
4. **`WHERE` 过滤右表列**让 `LEFT JOIN` **静默退化成 `INNER JOIN`**。
5. **`GROUP BY` 漏非聚合列**的引擎差异（见上表 ③ 类）。
6. **`WHERE` 里写聚合函数**（已实测报错）。
7. **`HAVING` vs `WHERE`**：含聚合的条件必须 `HAVING`；但 `WHERE` 能在分组前先减行、性能更好——**完全没提**。
8. **`SELECT *` 的危害**未作为 SQL 高频错误单列。

> 第 3 节末写着「每次发现新错误类型，追加到这里（**只增不改**）」——本次可直接追加这 8 条。

### 4.3 对话节奏问题

1. **SQL 一道题的推演成本远高于普通编程题，一轮 2 题已偏重。** 题 1 的评估要同时给出：学生的 SQL、结果集对照表、"自检为什么没拦住你"、正确 SQL、代改说明。实测**一轮评估约 1100 字**，学生读到一半注意力就断了——**断在长度上，不是断在难度上**。
   → SQL 轮**降到 1–2 题**，且同轮两题**必须是同一知识点的两面**（本仿真题 1 写 + 题 2 改错都是"配上没配上"，这个安排是对的）；长原理进 `🔍 多说一句` 折叠块。
2. **"两次追问"在 SQL 里几乎必然发生，而且性质不同——协议当成同一件事处理了。** 追问①（"两个都能跑看不出区别"）=**没看懂**；追问②（"为啥不报错啊，我还是觉得别扭"）=**不接受反直觉语义**。本仿真第一次换**表征**（表 → 类比），第二次换**可信度来源**（"别信我，你自己跑一遍对账 4 行 vs 1 行"）——**正因为第二次不再讲道理、而是甩出他自己跑出来的数字，才真正通**。→ 协议只说"换角度"，**没区分两种追问，也没写"用学生自己的执行结果当证据"这一招**。
3. **学生跑偏发生在"刚答完、还没被评估"的间隙，且这次是"好跑偏"。** 首评后他立刻质疑「能跑出来啊为什么算错」——**直接命中本领域核心冲突**。→ 建议协议加「**停车位**」：一句话确认 + 明确归还时间 + 不展开。本仿真验证有效。
4. **情绪低谷出现在"一轮 2 题 + 两题都判错 + 首次接触反直觉语义（NULL）"叠加时。** 原话：「我是不是不适合学数据库啊……报错我说不定还知道错在哪。」→ 有效顺序：**先肯定他这句话本身很敏锐（"你说到了 SQL 和别的语言最大的差别"）→ 再讲错 → 最后给可执行下一步**，把挫败点**转化成知识点**。
   → 更关键的观察：**"报错的教育价值"在本领域被彻底高估了**——**报错让他安心，不报错让他以为自己对了。** 本领域真正的教学难点不是"教他改错"，而是**教他不信任"没报错"**。

### 4.4 该学科特有的教学法发现（值得固化）

1. **⭐⭐「期望结果集 vs 实际结果集」对账表 —— 本仿真最有效的单一手段，也是 SQL 独有的。** 题 1 的杀招不是"你写错了"，而是这张表：学生**期望 3 行、SQL 也跑出 3 行、客户名一个不差，自检完整通过而答案是错的**（应为 4 行，含王五）——因为期望和 SQL 出自同一个错误模型。→ 升级为**出题硬要求：SQL 题必须填这张表，不许只交 SQL。**
   → ⭐ 这与 `编程.md` 第 5 节第 1 条「**能跑**：让学生说明结果是什么（**不用真跑**）」**直接冲突**。对 SQL，"不用真跑"是**危险的**：本仿真摸底 M2 学生"说得出 4 行"（对），正课却说"3 行"（错）。**SQL 直觉错误率远高于 Java，必须真跑**。
2. **⭐⭐「配对阶段 / 过滤阶段」两段式拆解 —— 讲 `ON` vs `WHERE` 的第一表征。**（阶段一 `ON` 决定谁和谁配、配不上也出行补 NULL；阶段二 `WHERE` 拿到临时表逐行删。）学生看完当场答出「WHERE 是把补 NULL 的行当普通行删了」。一次能解释三件事：`ON` vs `WHERE`、`LEFT JOIN` **退化成** `INNER JOIN`、为什么"左表保留"的保证会被 `WHERE` 废掉。
3. **⭐「数据集必须同时埋两种 NULL」的出题技巧。** 王五 = **无匹配行**（`o.id IS NULL`）；李四 = **匹配到了但值是 NULL**（`o.amount IS NULL`）。**两者在结果里长得一模一样**，语义完全不同。→ 这对数据是**制造静默错误的专用模具**，建议写进第 4 节作为 SQL 数据集最低要求。
4. **⭐"为什么不报错也能错"是 SQL 的必修心理课。** 学生依赖报错定位问题，SQL 恰恰**最贵的错一声不吭**。→ 固化话术：**「Java 的编译器替你挡错，SQL 不挡。语法对了只能说明它能跑，不说明它给了你想要的答案。所以每次都要问自己：期望几行？实际几行？」**
5. **⭐ 跨包借用有效，且现有机制本就允许。** SQL 的"结果正确性"判据不在 `编程.md`，但在 `理科.md` 第 1 节 + 第 5 节第 1 条「**代回验证**」——**"代回验证"就是 SQL 的"对账"**。→ `编程.md` 的 SQL 分支不必重造，直接引用即可。
6. **集合语义要先用「人话的角色化表述」铺一遍。** 本仿真类比链（**本子抄写 → 相亲会保安 / 散会复核 → 空格算不算不合格**）比任何定义都有效。→ 第 3 节加**表述纪律**：`JOIN` / `NULL` / 聚合**先用人话讲，术语最后补**。

### 4.5 学生画像补充（真实错误类型与困惑模式 → 可补 `编程.md` 第 3 节）

**A. 真实错误类型（本仿真实录，可直接追加）**

| # | 错误 | 哪里发生 | 为什么高危 |
|---|---|---|---|
| SQL-1 | **`LEFT JOIN` 写成 `JOIN`**，静默丢左表无匹配行 | 题 1 | 不报错；**期望 3 行、SQL 也跑出 3 行**，自检通过而答案错 |
| SQL-2 | 用「右表**可空列** `IS NULL`」当"存在性"判据 | 题 2 | 不报错，**静默多捞出行**（把有订单但金额为空的李四也捞了） |
| SQL-3 | 把 `NULL` 当 `0` / 空字符串 | 摸底 M3、题 1 | `WHERE` 静默排掉整行；`NULL <> NULL` 是 NULL 不是 FALSE |
| SQL-4 | 把「金额是 NULL」读成「没有订单」 | 题 1、题 2 | **一条误解同时毁掉两道题**，且极常见 |
| SQL-5 | `WHERE` 过滤右表列，把 `LEFT JOIN` **退化成 `INNER JOIN`** | 题 1 的另一半 | 不报错，"左表保留"静默失效 |
| SQL-6 | `WHERE` 里写聚合函数 | 摸底已实测 | 报错（`misuse of aggregate`）→ **属少见的"会报错"，反而好抓** |
| SQL-7 | `COUNT(*)` / `COUNT(列)` / `COUNT(DISTINCT 列)` 混用 | 数据集专门埋了 | 三者对王五分别给 1 / 0 / 0，**都不报错** |
| SQL-8 | 隐式逗号连接漏 `WHERE` → 笛卡尔积 | 数据集可复现（16 行） | 不报错，行数爆炸但不一定被注意到 |
| SQL-9 | `GROUP BY` 漏非聚合列 | 题 1 复评时补讲 | **引擎相关**：SQLite 静默容忍，MySQL 8.0 `ONLY_FULL_GROUP_BY` → 报错 |

**B. 困惑模式（比错误类型更值得记的操作信息）**

1. **⭐ 判据是「没报错 = 写对了」。** 原话：「报错我说不定还知道错在哪；这种一声不响的我是真没辙。」——**运维出身 + CRUD 思维的典型水位**（习惯"跑不通就修到跑通"）。SQL 把这条判据彻底废掉了。**建议列为"必须优先拆掉的错误心智模型"第一位。**
2. **⭐ 把"不保险就加上"当技术决策依据。** 摸底 M1：「LEFT JOIN 我一般就是觉得不保险就加上」——**没有"需求 → 实现"推理链**。需强制"先说业务需求，再选 JOIN 类型"。
3. **先假定别人错，不细读题面。** 题 2 答"应该改成 LEFT JOIN"——题面那句**本来就是 `LEFT JOIN`**。→ SQL 改错题**强制先复述题面需求**再作答。
4. **对"反直觉语义"的第一反应是不接受，不是记下来。** 追问②「结果不一样但都能跑，为啥不报错啊，我还是觉得别扭」。→ 要给**可验证的把手**，而不是继续讲道理。
5. **面试动机是强触发点**：课程绑到"面试必问"时，追问变少、专注度上升。
6. **他需要"停车位"**：答完题后插话质疑不是捣乱，是**真实需求溢出**。→ ⏳ 待办留一栏收这类问题。
