## 1. Three-dimension definitions

| Dimension | Name | What it judges | What a typical ✅ looks like |
|---|---|---|---|
| ① | **Conceptual understanding** | Knows what this thing is, why it exists, and when to use it | Can explain "encapsulation = hide details + control access" instead of just reciting `private` |
| ② | **Logical correctness** | The algorithm / flow / boundaries / data-structure choice are right and produce the correct result | The sum loop's `i < arr.length` boundary is right; picks HashMap rather than ArrayList for counting |
| ③ | **Compilability** | The code is **structurally** correct and runs in the IDE / interpreter | Class and method nesting levels are right, reserved words used correctly, `return` matches the return type |

> **Dynamic languages (JavaScript / Python / SQL etc.)**: ③ is judged as **"runtime correctness"** —
> syntactically valid but wrong at runtime (`this` bound wrong, implicit type coercion, `LEFT JOIN` dropping rows)
> also lands in ③. Three counter-criteria to self-check:
> **no error ≠ correct | right output ≠ correct | right once ≠ correct**.

### 1.1 Boundary cases: which dimension does this error belong to? (contested ones only)

The general arbitration principle is in `协议/00_导师协议.en.md` §3 (**said it wrong → ①; thought it wrong → ②; wrote it wrong → ③**).
High-frequency boundaries in programming:

| Case | Verdict | Why |
|---|---|---|
| **Insufficient algorithmic complexity** (brute force passes, but risky) | **② ⚠️** | The result is right but the approach doesn't hold — that is "thinking", not "writing". ③ judges "does it run", and it **does** run, so it must never go to ③ |
| **Code runs but the result is wrong** (`==` comparing Strings, `i <= arr.length`) | **② ❌** | Logic error. Note: the out-of-bounds throws, but it is **first of all a boundary-logic problem**, not a syntax problem |
| **Compiles but is semantically wrong** (`volatile int i; i++` atomicity / visibility) | **② ❌** | Compiles, often runs correctly, but the semantics don't hold. **This is what interviews actually screen for**; ③ cannot reach it |
| **Concept confusion** (calling overriding "overloading", describing `ArrayList` as `LinkedList`) | **① ❌** | The student "said it wrong", not "wrote it wrong" |
| **Calling a non-existent method** (e.g. `printlin`) | **③ ❌** | Structural error (unresolvable). ⚠️ But if it is **clearly a typo** (`printlin` for `println`) → see the exemption rules in §2 |
| **Skipped steps but complete reasoning** (no intermediate variable, one line) | **③ ⚠️** | The reasoning holds; the expression is merely incomplete |
| **Poor naming** (`a`, `b`, `x1`) | **③ ⚠️** (minor) | A form issue; usually noted rather than deducting a dimension |

> **How to use this table**: consult it only when you **genuinely cannot decide**. Most errors settle in one step via the arbitration principle.

## 2. Dimension ③ criteria (strictly separate "structural errors" from "slips")

### ❌ Structural errors that must lose points

- The `main` method declared outside the class
- Another `public class` nested inside a class (top-level class rule)
- Using a reserved word (`class`, `int`, `for`…) as a variable name
- Wrong method signature: a `void` method that `return`s a value; a typed method with no `return`
- Calling a member that doesn't exist / argument count not matching the signature
- A required import is missing **and** it is *not* a "student marked it as omitted" case
- A loop condition that guarantees an infinite loop or guarantees no execution (**kills both logic and syntax**)
- A variable used before it is declared / a type mismatch (e.g. assigning a `String` to an `int`)

### ⚠️ Exemptable slips (no points lost, not corrected line by line)

- Full-width punctuation: `；` `（）` `‘’` `“”`, mixed CJK/Latin punctuation
- Missing semicolons, extra spaces (e.g. `System.out .println`)
- Case / spelling slips: `ArryList`, `printlin`, `string` (when it is obviously a slip)
- Missing `import`, missing `class` wrapper, omitted `main` (**when the student marks it as omitted**)
- Code fence tagged with the wrong language (```python around Java) — that is a Markdown problem, not a code problem

## 3. High-frequency error checklist for this subject (watch these during assessment)

1. Using a comma as the separator in a `for` loop (`for (int i = 0, i < n, i++)`)
2. Missing closing brace / unbalanced brackets
3. Constructor written as `public void Car(...)` (extra `void`)
4. A field already initialised, masking the fact that the constructor was never written
5. Calling a non-static method directly from `static main`
6. Creating a member inner class without `outer.new Inner()`
7. Comparing `String` / object contents with `==` (should be `.equals()`)
8. Array out of bounds: `i <= arr.length`
9. Modifying a collection while iterating over it (`ConcurrentModificationException`)
10. Referencing a variable outside its scope (declared inside an `if` block, used outside it)

> Every time you find a new error type, append it here (**append-only**) — the more this list is used, the more accurate it gets.

## 4. Question forms (how to set questions so they mean something)

| Round | Question type | Key points |
|---|---|---|
| Round 1 | **Concept questions** (1–2) | Ask "why" rather than "what": e.g. "Why is `String` immutable?" |
| Round 2 | **Write code** (2) | Must **change the conditions** (new data, new constraint, new edge case); never copy the worked example |
| Round 3 | **Synthesis question** (1) | Combine several earlier knowledge points into one small feature |

### This subject's question cost: **light → heavy (by sub-field)**

Per the "question cost scaling" in `协议/00_导师协议.en.md` §2:

| Sub-field | Question type | Cost | Per round |
|---|---|---|---|
| Language basics / syntax | Concept Q&A, short code, true/false | Light | up to 3 |
| Language basics | Ordinary code question | Medium | 2 |
| **Algorithms & data structures** | **A full algorithm problem** (approach + code + complexity + edge cases) | **Heavy** | **1–2** |
| **SQL / databases** | Multi-table query + result walk-through | **Heavy** | **1–2** |

> **Why algorithms and SQL are "heavy"**: a full algorithm problem has 4 sub-parts
> (state the approach → write the code → state the complexity → discuss edge cases) and the simulation measured
> **2 questions consuming 8 round-trips**; SQL's silent errors force a concrete data walk-through, i.e. two tables per question.
> See [`../docs/simulations/03-编程-算法数据结构.md`](../docs/simulations/03-编程-算法数据结构.md) and
> [`04-编程-SQL数据库.md`](../docs/simulations/04-编程-SQL数据库.md).
>
> **Allowed**: "one round = one full algorithm problem" is perfectly compliant — as long as approach/code/complexity/edge cases
> are one complete answer. **Forbidden**: three full algorithm problems in one round.

> **Send only 1–3 questions per round, and send the next round only when this round is all ✅** (see §2 of `协议/00_导师协议.md`).
> Don't send all three rounds' questions at once.

**What a good code question looks like**:
- Has a clear input and output (verifiable)
- Hides one boundary condition (empty array, 0, negative number, duplicate values)
- Uses this lesson's knowledge points but requires nothing not yet learned

**Forbidden**:
- ❌ Asking "please restate the content of section 3"
- ❌ Asking something that needs knowledge not yet learned
- ❌ Asking something with no clear right or wrong (e.g. "what do you think of language X")

## 5. Verification methods (how to confirm the student really knows it)

1. **Does it run**: have the student state what this code outputs (they don't have to actually run it, but must be able to say)
2. **Change the scenario**: swap the conditions and ask "if this became X, would your code still work? Why?"
3. **Push the boundaries**: ask "what happens if the input is empty / 0 / extremely long?"
4. **Explain**: have the student describe in their own words what this code is doing
5. **Fix the bug**: give them buggy code and have them find it

> "Can recite the syntax" is not mastery; **"can still write it correctly in a new scenario" is**.

### How to use the Feynman technique in programming

| Topics worth a Feynman question | Not worth it (don't waste time) |
|---|---|
| Abstract mechanisms: closures, pass-by-reference, polymorphism, recursion | Syntax details: how `for` is written, where `import` goes |
| Design rationale: "why do we need interfaces", "why is String immutable" | The parameter order of a specific API |
| Easily confused concepts: `==` vs `equals`, pass-by-value vs pass-by-reference | What a function returns |
| Architectural thinking: why we layer, what dependency injection is | Environment setup steps |

**Special constraints for programming Feynman questions**:

- ❌ **No code may appear in the explanation** ("don't write code, use words") — otherwise the student just pastes code and understanding can't be measured
- ✅ Everyday analogies are allowed ("a closure is like a backpack you carry with you")
- ✅ Follow-up Feynman: "you used the backpack analogy for a closure — so what can go in the backpack? When does the backpack get thrown away?"

**Typical wording**:

```
No code, and these words are banned: <scope>, <reference>, <closure>

In words your mum could follow, explain: why does this function "remember" the variable outside it?
```

## 6. No further-reading list

**Do not** hand the student a list like "required reading: <book> §7.1–7.3" — see §8 of `协议/00_导师协议.md`:
a book title and chapter number recalled from memory can't be verified, and the student probably doesn't own that book.

**All teaching content goes into that lesson's teaching guide**, written out by the tutor.

**If the student has their own material** (a textbook, docs or notes inside `资料/`) → **teach directly from what's actually in it**,
and cite "from `<filename>`, `<specific section/page>`" — that's a real, checkable citation, not a memory recall.
